## 结论

这次没有打到并发上限。全套没有 HTTP 429、HTTP 502、连接重置，也没有冷却或封禁。日志末尾的人工修正覆盖了脚本自动写出的「不要依赖 >5 并发」：那句话只是因为某个 PASS 档 ≥5 就触发的保守规则，和这次实测不符。

修正后的结论：可以作为单人日常的纯聊天后端；这次也撑住了中等扇出（测到 50 个在途请求，以及约 2 请求/秒的混合流量，持续数分钟），没有封禁。不要信任大约 8k 字符以上的上下文（硬切断在最后 12000 个字符，前缀被静默丢掉，没有服务端上下文压缩）。不要信任 `max_tokens`、model id、`finish_reason` 和 `usage`。除非想要 SSE，否则必须显式传 `stream: false`。这不是官方 API，上游可以在本地代码不变的情况下改掉。

本代理只提供 `GET /health`、`GET /v1/models`、`POST /v1/chat/completions`。上游是有道网页 LLM（`deepseek_r1`）。可以接到 Codex 等客户端当聊天模型，但下列能力本代理不提供，需要客户端自己或其他正规 API：

- `tools` / `function_call`（工具调用）
- 画图、图像生成，以及多模态输入输出
- 子 agent / 多 agent 编排 API
- 服务端上下文压缩（仅硬截最后 12000 字）
- `max_tokens`、`usage`、按 model id 路由真实上游模型
- Codex 等客户端的高级能力（新绘画、子 agent、压缩上下文等）

case1 到 case11 的 VERDICT 全部是 PASS。

## 硬限制

- 本地请求体 1MB，超过直接 400，不会打上游。
- 拼好的对话文本只保留最后 12000 个 JS 字符（`slice(-12000)`）。更长上下文静默丢前缀，HTTP 仍可能是 200。1k、4k、8k 能同时回显 HEAD 和 TAIL；16k 为 23.30s，32k 为 42.48s。
- 单请求链路固定 3 次上游调用。50 路并行这次仍然成功，这个倍数当天没有触发可见配额。
- 无 `usage`。`finish_reason` 恒为 `stop`。不转发 `max_tokens` / `temperature`。model id 不参与上游选择。
- 省略 `stream` 时响应是 `text/event-stream`。
- 不支持 `tools` / `function_call`、画图与多模态、子 agent / 多 agent 编排，也不做服务端上下文压缩。Codex 等客户端只能把它当纯聊天后端；那些高级能力要由客户端自己或其他正规 API 提供。
